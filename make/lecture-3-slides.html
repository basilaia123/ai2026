🌉 Recap: აგენტებიდან ➔ API-მდე

გუშინ: ლოკალური აგენტები (MCP)

წინა ლექციაზე ვნახეთ, როგორ კითხულობს AI ჩვენს ლოკალურ ფაილებს.

მაგრამ რა ხდება, როცა AI-ს სჭირდება სხვადასხვა სისტემების (Google Sheets, CRM, Telegram) დაკავშირება ერთმანეთთან ინტერნეტში?

დღეს: ვების უნივერსალური ენა

იმისათვის, რომ ნებისმიერ აპლიკაციას ვესაუბროთ კოდის გარეშე, ჩვენ უნდა ვისწავლოთ მათი ენა:

  • API: კარიბჭე ინფორმაციის მისაღებად.
  • JSON: ენა, რომლითაც პროგრამები საუბრობენ.
  • Webhooks: სისტემა, რომელიც მომენტალურად გვატყობინებს სიახლეს.

არანაირი პროგრამირება! (Google Antigravity)

ნუ შეგეშინდებათ რთული ტერმინების. დღეს ჩვენ გამოვიყენებთ Google Antigravity-ს, რომელიც ყველა რთულ JSON კოდს ჩვენ მაგივრად დაწერს!

🚦 გამომწვევები vs. მოქმედებები

🚀 გამომწვევი (Trigger)

გამომწვევი არის ის მოვლენა, რომელიც იწყებს სცენარს.

ტიპები:

  • მომენტალური (Instant): Webhook-ის საშუალებით
  • დაგეგმილი (Scheduled): დროის მიხედვით
  • პერიოდული შემოწმება (Polling): პერიოდულად ამოწმებს

📌 გამომწვევის მაგალითები

  • 📧 ახალი ელფოსტა Gmail-ში
  • 📄 ახალი ფაილი Google Drive-ში
  • 📝 ფორმის ახალი გამოგზავნა
  • 🕐 ყოველდღე დილის 9 საათზე
  • 💬 ახალი შეტყობინება Slack-ში

⚡ მოქმედება (Action)

მოქმედება არის ის, რასაც აკეთებს სცენარი გამომწვევის შემდეგ.

ტიპები:

  • შექმნა (Create): ახალი ჩანაწერის შექმნა
  • განახლება (Update): არსებულის განახლება
  • წაშლა (Delete): წაშლა
  • ძიება (Search): მოძიება

📌 მოქმედების მაგალითები

  • ➕ სტრიქონის დამატება Google Sheets-ში
  • 📤 ელფოსტის გაგზავნა Gmail-ის საშუალებით
  • 💾 ფაილის შენახვა Dropbox-ში
  • 📊 Notion-ის გვერდის შექმნა
  • 💬 პოსტის გამოქვეყნება Slack-ის არხზე

🔄 ტიპიური სამუშაო პროცესის პატერნი

გამომწვევი (რამე მოხდა) → მოქმედება 1 (შემოწმება) → მოქმედება 2 (დამუშავება) → მოქმედება 3 (შედეგის შენახვა/გაგზავნა)

🔔 Webhooks - მომენტალური გამომწვევები

რა არის Webhook?

Webhook - მომენტალური შეტყობინება: „რაღაც მოხდა!"

განსხვავებით პერიოდული შემოწმებისგან (ყოველ 15 წთში შემოწმება), Webhook მაშინვე აგზავნის სიგნალს.

📊 პერიოდული შემოწმება (ნელი)

Make.com ამოწმებს ყოველ 15 წუთში:

  • 09:00 - შემოწმება (არაფერი)
  • 09:15 - შემოწმება (არაფერი)
  • 09:30 - შემოწმება (ახალი ელფოსტა!)

დაყოვნება: 0-15 წუთი

⚡ Webhook გამომწვევი (სწრაფი)

აპლიკაცია აგზავნის სიგნალს მაშინვე:

  • 09:27:43 - ელფოსტა მოვიდა → Webhook!
  • მომენტალურად სცენარი იწყება

დაყოვნება: წამები

💡 ცხოვრებისეული ანალოგია: "კარის ზარი vs ფანჯარაში ყურება"

პერიოდული შემოწმება (Polling): ჰგავს იმას, რომ ყოველ 5 წუთში ფანჯარასთან მიხვიდეთ და გაიხედოთ - მოვიდა თუ არა კურიერი (დამღლელია და დრო იკარგება).
Webhook: ჰგავს კარის ზარს - თქვენ მშვიდად აკეთებთ თქვენს საქმეს. როდესაც კურიერი მოვა, ზარს თითს დააჭერს და თქვენ მაშინვე იგებთ ამას!

🔧 როგორ გამოვიყენოთ Webhook?

კონფიგურაციის ნაბიჯები:

  1. ➕ დაამატეთ "Webhooks" მოდული → "Custom Webhook"
  2. 🔗 Make გამოიტანს Webhook URL-ს (უნიკალური)
  3. 📋 დააკოპირეთ URL
  4. ⚙️ გადადით აპლიკაციაში და ჩასვით Webhook URL
  5. ✅ ტესტი - გააკეთეთ რამე აპლიკაციაში

🎯 Webhook-ის მაგალითები

  • Stripe: გადახდა მიღებულია → მომენტალური ქვითარი
  • Typeform: ფორმა გამოგზავნილია → მაშინვე ელფოსტა
  • GitHub: ახალი commit → Slack შეტყობინება
  • Shopify: ახალი შეკვეთა → CRM-ის განახლება

⚠️ Webhook-ის უსაფრთხოება

  • Webhook URL არის საიდუმლო - არ გააზიაროთ საჯაროდ
  • ვინც იცის URL, მას შეუძლია სცენარის გაშვება
  • გამოიყენეთ Webhook-ის ვალიდაცია როცა შესაძლებელია

🧩 ფილტრები

ფილტრი - პირობა, რომელიც წყვეტს გაგრძელდება თუ არა შესრულება

IF (პირობა არის TRUE) → გაგრძელდება
ELSE → გამოტოვდება (skip)

ფილტრის მაგალითი

  • Gmail → ფილტრი → Google Sheets
  • ფილტრის პირობა: Subject contains "Invoice"
  • შედეგი: მხოლოდ ინვოისები გადის Sheets-ში

🔀 მარშრუტიზატორი

მარშრუტიზატორი - ყოფს ნაკადს მრავალ შტოდ (branches)

მარშრუტიზატორის მაგალითი: ელფოსტის კატეგორიზაცია

სცენარის სტრუქტურა:
Gmail გამომწვევი
  ↓
მარშრუტიზატორი
  ├─ [შტო 1] Subject contains "Urgent" → Slack შეტყობინება
  ├─ [შტო 2] From contains "@client.com" → CRM-ის განახლება
  └─ [შტო 3] Has attachment → Drive-ში შენახვა

თითოეულ შტოს აქვს საკუთარი ფილტრი!

🏗️ სრული Workflow არქიტექტურა

1. TRIGGER: Shopify Webhook (New Order) ↓ 2. DATA EXTRACTION: • Customer: {{name}}, {{email}} • Order: {{order_id}}, {{total}} • Items: {{line_items}} (Array) ↓ 3. ROUTER (3 Branches): Branch 1: Customer Communication ├─ Gmail Module ├─ Subject: "Order #{{order_id}} Confirmed" └─ Body: Template with order details Branch 2: Inventory Update ├─ ITERATOR (loop through items) ├─ Google Sheets (Search Row by SKU) ├─ Math: Current Stock - Ordered Quantity └─ Google Sheets (Update Stock) Branch 3: Team Notification ├─ FILTER: If total > $500 ├─ Slack Module └─ Message: "🎉 High-value order: ${{total}}" ↓ 4. 🔀 Advanced Router & Filter Scenarios

🎯 რთული ლოგიკის აგება

📊 Multiple Conditions (AND/OR)

AND: ყველა პირობა უნდა იყოს TRUE

Filter: Subject contains "Urgent" AND Priority = "High" AND Time < 9:00 AM

OR: ერთი პირობა მაინც TRUE

Filter: From = "boss@company.com" OR Subject contains "CRITICAL"

🔁 Nested Routers (Router-ში Router)

Email Trigger ↓ ROUTER 1 (Department) ├─ Branch: Sales │ ↓ │ ROUTER 2 (Priority) │ ├─ High → Slack + CRM │ └─ Normal → CRM only │ ├─ Branch: Support │ → Zendesk Ticket │ └─ Branch: Other → Archive

🧮 Advanced Filter Operators

Operator მაგალითი გამოყენება
Contains Subject contains "invoice" ტექსტის ძებნა
Regex Match Email matches /^\d{3}-\d{4}$/ რთული პატერნები
Greater/Less Amount > 1000 რიცხვითი შედარება
Exists Attachment exists Field-ის არსებობა
Date/Time Date > "2024-01-01" თარიღების შედარება

💡 ცხოვრებისეული ანალოგია: "გზაჯვარედინის ჭკვიანი შუქნიშანი"

Router (მარშრუტიზატორი): ჰგავს ჭკვიან შუქნიშანს ოთხმხრივ გზაჯვარედინზე. როდესაც შემოდის მონაცემების "მანქანა", შუქნიშანი ამოწმებს მის ნომერს (Filter):
• თუ VIP კლიენტია ➔ ანთებს მწვანეს მარჯვნივ (გადადის Sales დეპარტამენტის Slack-ში);
• თუ ტექნიკური ხარვეზია ➔ ანთებს მწვანეს მარცხნივ (იგზავნება Support-ის ბაზაში);
• ყველა დანარჩენი (Fallback) ➔ მიდის პირდაპირ (არქივში).

💡 Best Practices - Routers & Filters

  • Default Branch: Router-ს ყოველთვის ჰქონდეს "fallback" route
  • Test Each Branch: ცალ-ცალკე ტესტირება
  • Name Your Branches: "High Priority", "Low Priority", etc.
  • Use Variables: პირობებში გამოიყენე {{variables}}

🔐 Connection Setup

საჭირო ინფორმაცია:

  • Host: database server address (e.g., db.example.com)
  • Port: 3306 (MySQL), 5432 (PostgreSQL)
  • Database Name: your_database
  • Username & Password: credentials
  • SSL: enable if required

⚠️ Security Best Practices

  • Read-Only User: შექმენი limited permissions user Make-ისთვის
  • Whitelist IPs: მხოლოდ Make.com IPs-ებზე წვდომა
  • Never Expose Credentials: არასოდეს გააზიარო database details
  • Use Prepared Statements: SQL injection-ის თავიდან აცილება
  • Regular Backups: ყოველთვის backup before automation

რა არის API? 🤔

API = Application Programming Interface

API არის „ენა", რომლითაც სხვადასხვა პროგრამა ერთმანეთს ესაუბრება

💡 ცხოვრებისეული ანალოგია: "რესტორნის ოფიციანტი"

კლიენტი (თქვენ): სხედხართ მაგიდასთან და სამზარეულოში შესვლა არ გჭირდებათ.
მენიუ (API დოკუმენტაცია): ჩამონათვალი, თუ რისი მოთხოვნა შეგიძლიათ.
ოფიციანტი (API Request): იღებს თქვენს შეკვეთას, გადასცემს მზარეულს (სერვერს) და უკან მოაქვს მზა კერძი (მონაცემების პასუხი/JSON)!

რესტორანში

  • მენიუ - რა შეგიძლია შეუკვეთო
  • ოფიციანტი - გადმოსცემს შენს შეკვეთას
  • სამზარეულო - ამზადებს საკვებს
  • შედეგი - იღებ თეფშს

API-ში

  • დოკუმენტაცია - რა შეგიძლია მოითხოვო
  • API მოთხოვნა - გაგზავნი მოთხოვნას
  • სერვერი - ამუშავებს მოთხოვნას
  • პასუხი - იღებ მონაცემებს

მთავარი იდეა

API საშუალებას გვაძლევს „შევუკვეთოთ" მონაცემები ან ფუნქციონალობა სხვა პროგრამებსა და სერვისებს, ისევე როგორც რესტორნის მენიუდან ვუკვეთავთ საჭმელს.
